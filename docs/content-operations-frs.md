الهدف: تحويل الأفكار العشر الواردة في المقال إلى نظام متكامل داخل CMS لإدارة إنتاج المحتوى، بدءًا من اكتشاف احتياجات الجمهور وحتى النشر والتوزيع وقياس الأداء وتحسين المقالات.

راجعت المقال وموقع لوسيل. المقال يركز على بناء عملية تحريرية قابلة للتكرار، بدل زيادة عدد المقالات دون ضبط الجودة. كما أن لوسيل تنشر حاليًا أدلة عملية ومسارات مهام وكورسات، لذلك سنصمم النظام لإدارة الأنواع الثلاثة معًا، وليس المقالات التقليدية فقط.&#x20;

وستعمل جميعها فوق نظام المقالات الحالي، دون إنشاء CMS منفصل أو التأثير على الروابط المنشورة.

هذه الوظائف ليست نقلًا حرفيًا من المقال؛ بل إضافات ضرورية لطبيعة الأدلة الحكومية والخدمات الرقمية في لوسيل.

| ID     | Feature                | السلوك                                                                             |
| ------ | ---------------------- | ---------------------------------------------------------------------------------- |
| LX-001 | Source Registry        | سجل موحد للجهات والمصادر الرسمية وروابطها وحالة التحقق                             |
| LX-002 | Freshness Monitor      | متابعة الأدلة التي تعتمد على رسوم أو مواعيد أو شروط قد تتغير                       |
| LX-003 | Claim Verification     | ربط الادعاءات المهمة بمصدر وتاريخ تحقق ومسؤول                                      |
| LX-004 | Existing Content Audit | تصنيف المحتوى المنشور إلى إبقاء أو تحديث أو دمج أو حذف/إعادة توجيه بعد المراجعة    |
| LX-005 | Indexing Monitor       | استقبال بيانات التغطية والفهرسة المتاحة من Google دون افتراض أن النشر يعني الفهرسة |
| LX-006 | Demand-to-Content      | تحويل مشكلة معتمدة من الرادار إلى فكرة ومهمة وBrief دون إعادة الإدخال              |

## 5. Data Model — تصميم قاعدة البيانات

للتنفيذ المقترح على PostgreSQL / Supabase، نستخدم سجلًا أساسيًا موحدًا للمحتوى يربط الأدلة والمسارات والكورسات الموجودة بالفعل، مع إضافة جداول لإدارة العملية التحريرية.

| Table                   | الغرض                                          |
| ----------------------- | ---------------------------------------------- |
| `content_items`         | معرف موحد ونوع المحتوى وربطه بسجل النشر الحالي |
| `content_ideas`         | الفرص والأفكار التحريرية                       |
| `idea_evidence`         | الأدلة والمصادر المرتبطة بكل فكرة              |
| `topic_clusters`        | المجموعات الموضوعية                            |
| `cluster_members`       | العلاقات بين المحتوى والمجموعات                |
| `content_briefs`        | الموجز التحريري وإصداراته                      |
| `content_outlines`      | الهياكل المعتمدة                               |
| `workflow_stages`       | تعريف مراحل العمل                              |
| `workflow_tasks`        | المهام والمسؤوليات والمواعيد                   |
| `content_reviews`       | تقييمات وملاحظات المراجعين                     |

# Implementation Brief — Lusaill Content Operations

**Feature:** Content Operations Dashboard\
**Scope:** Implement modules FR-001 through FR-070 and LX-001 through LX-008 from the approved functional specification.

## Technical instructions

1. Inspect the existing repository, database schema, CMS routes, authentication system, and publishing workflow before modifying anything.
2. Build the dashboard inside the existing admin interface. Reuse current design components, typography, RTL layout, authentication, and database conventions.
3. Preserve existing articles, guides, courses, task paths, slugs, canonical URLs, and public SEO metadata.
4. Create a unified content operations data model linked to the existing content tables, with schema migrations and access policies.
5. Implement the operational dashboard, idea backlog, topic clusters, editorial briefs, outline builder, workflow board, and quality review screens.
6. Implement server-enforced role permissions and workflow transition rules. A writer must not bypass required review or publish without authorization.
7. Record all important edits, review decisions, publication operations, and workflow transitions in an immutable audit history.
8. Integrate the current publishing flow with scheduling, post-publication validation, and safe retries.
9. Add AI-assisted research and drafting only as optional, auditable functions. Require source verification and human editorial approval.
10. Provide loading, empty, success, and error states throughout the interface. Do not use hardcoded demo metrics as production data.
11. Add unit and integration tests for permissions, workflow transitions, publish gating, migrations, and publishing.
12. Deliver the implementation in incremental, reviewable stages without breaking existing public functionality.

## Definition of Done

- All P0 features work with persisted data.
- Existing published content remains accessible.
- Role-based permissions are enforced server-side.
- Critical quality failures block publication.
- Dashboard metrics reflect real database records.
- Editorial actions are traceable.
- Arabic RTL desktop and mobile layouts work correctly.
- Automated tests pass.
- Deployment and rollback instructions are documented.
